# De Node/PostgreSQL a Supabase

Qué hay hoy, a qué equivale en Supabase y qué falta. Este documento está pensado para trabajar de abajo hacia arriba: primero base de datos, luego Auth, productos, Storage y por último el panel admin.

**Regla del plan maestro:** Node no se borra hasta pasar la prueba de paridad (fase 7). Todo lo de abajo se prepara al lado, sin tocar `backend/` ni `frontend/js/api.js`.

## 1. Archivos ya listos en esta rama

| Archivo | Qué es | Probado |
|---------|--------|---------|
| `supabase/migrations/0001_schema.sql` | Tablas, índices, triggers, RLS y bucket de Storage | Sí: se ejecutó completo en PostgreSQL 17 con un `auth` y un `storage` de prueba, y se verificaron las políticas con un anónimo, una cliente y un admin |
| `supabase/seed.sql` | Los 7 productos que ya existen | Sí, en la misma prueba |
| `.env.example` | Variables con marcador de posición | — |
| `frontend/js/supabase-client.js` | Cliente de Supabase con marcadores; no lo importa ninguna página | No se probó contra un proyecto real (todavía no existe) |

Lo que **no** se pudo probar sin un proyecto de Supabase real: el envío de correos, Google OAuth, las políticas de `storage.objects` con el servicio de Storage de verdad y los límites de intentos de Auth.

## 2. Tablas

| Tabla actual (`database/`) | Tabla en Supabase | Cambios |
|----------------------------|-------------------|---------|
| `usuarios` | `auth.users` + `public.profiles` | La clave y el correo pasan a Auth. `profiles` guarda `first_name`, `last_name`, `phone`, `role` (`customer`/`admin`), `is_active` y una copia de `email` para el panel admin. Desaparecen `password`, `google_id` y `auth_provider` (Auth guarda las identidades) |
| `tokens_recuperacion` | — | Auth guarda y vence los códigos. Se elimina |
| `productos` | `public.products` | Columnas en inglés, igual al modelo `Product` del plan. Agrega `slug`, `flavor`, `short_description`, `volume`, `accent_color`, `is_featured`, `sort_order`. Mantiene `stock`, `badge_*`, `discount_percent` |
| `carrito`, `carrito_items` | `carts`, `cart_items` | Igual que antes. Hoy ninguna parte de la web las usa |
| `pedidos`, `detalles_pedido` | `orders`, `order_items` | Igual que antes. Hoy ninguna parte de la web las usa. Solo un admin puede escribir |

Equivalencia de columnas de `productos`:

| Antes | Ahora |
|-------|-------|
| `nombre` | `name` |
| `descripcion` | `description` |
| `precio` | `price` |
| `stock` | `stock` |
| `imagen_url` | `image_url` |
| `categoria` | `category` |
| `activo` | `is_active` |
| `letrero` | `badge_text` |
| `letrero_tipo` | `badge_type` |
| `descuento` | `discount_percent` |
| `color_fondo` | `background_color` |

Cambios de tipo: `SERIAL` pasa a `bigint generated by default as identity`; `TIMESTAMP` pasa a `timestamptz`; los `VARCHAR(n)` pasan a `text` con `CHECK` de largo donde importa. `usuarios.rol = 'cliente'` pasa a `'customer'`.

## 3. Endpoints de la API actual y su equivalente

### Autenticación

| API actual | Equivalente en Supabase | Edge Function |
|------------|-------------------------|---------------|
| `POST /api/auth/registro` | `supabase.auth.signUp({ email, password, options: { data: { first_name, last_name, phone } } })`. El trigger `handle_new_user` crea el perfil. Largo mínimo de clave 8 en Authentication > Providers > Email | No |
| `POST /api/auth/login` | `signInWithPassword`. Después leer `profiles.is_active`; si es `false`, `signOut()` y avisar | No |
| `POST /api/auth/google` | `signInWithOAuth({ provider: 'google' })` o `signInWithIdToken` si se conserva el botón de Google actual. Se reutiliza el proyecto de Google Cloud | No |
| `POST /api/auth/recuperar` | `resetPasswordForEmail(email)`. Para mantener el código de 6 dígitos, poner `{{ .Token }}` en la plantilla de correo | No |
| `POST /api/auth/reset-password` | `verifyOtp({ email, token, type: 'recovery' })` y luego `updateUser({ password })` | No |
| `GET /api/auth/perfil` | `from('profiles').select().eq('id', user.id).single()` | No |
| `PUT /api/auth/perfil` | `from('profiles').update({ first_name, last_name, phone })` | No |
| `PUT /api/auth/cambiar-password` (con clave actual) | Comprobar la actual con `signInWithPassword` y luego `updateUser({ password })` | No |
| `PUT /api/auth/cambiar-password` (con código) y `POST /api/auth/perfil/codigo-password` | `reauthenticate()` envía el código; luego `updateUser({ password, nonce })` | No |
| `/api/auth/profile`, `/change-password` | Duplicados en inglés que el frontend no usa. No se migran | — |
| Límite de intentos (`rateLimit.js`) | Límites propios de Supabase Auth | No |
| Correo de bienvenida y de "clave cambiada" (`mailService.js`) | Los de recuperación y confirmación salen de las plantillas de Auth con SMTP propio. El de bienvenida es opcional | Solo si se quiere bienvenida |

### Productos

| API actual | Equivalente en Supabase | Edge Function |
|------------|-------------------------|---------------|
| `GET /api/products` | `from('products').select('*').order('sort_order')`. La política deja leer solo los publicados; un admin ve todos, así que desaparece `includeInactive` | No |
| `GET /api/products/:id` | `.eq('id', id).single()` o `.eq('slug', slug)` | No |
| `POST /api/products` | `.insert({...})`. Las validaciones de `productController.js` (precio, stock, color hex, tipo de letrero, descuento máx. 80) ya están como `CHECK` en la tabla; en el navegador se repiten con un esquema para mostrar mensajes en español | No |
| `PUT /api/products/:id` | `.update({...}).eq('id', id)` | No |
| `DELETE /api/products/:id` (borrado lógico) | `.update({ is_active: false })` | No |
| `DELETE /api/products/:id/permanent` | `.delete().eq('id', id)` | No |
| `POST /api/upload` | `storage.from('product-images').upload(ruta, archivo)` y `getPublicUrl(ruta)`. Bucket con los mismos límites de Multer: 5 MB y JPG, PNG, WEBP, GIF | No |
| `GET /uploads/*` | URL pública del bucket | — |

### Usuarios (panel admin)

| API actual | Equivalente en Supabase | Edge Function |
|------------|-------------------------|---------------|
| `GET /api/users` | `from('profiles').select('id,email,first_name,last_name,phone,role,is_active,created_at')`. La política deja leer todos solo a un admin | No |
| `PATCH /api/users/:id/activo` | `from('profiles').update({ is_active })`. El trigger impide que un admin se desactive a sí mismo | **Sí, recomendada**: `profiles.is_active` solo marca; para bloquear de verdad el inicio de sesión hay que banear al usuario en Auth, y eso exige la clave `service_role`, que nunca puede estar en el navegador |

### Otros

| API actual | Equivalente | Edge Function |
|------------|-------------|---------------|
| `GET /api/health` | No hace falta | No |
| `GET /` | No hace falta | No |

### Resumen de Edge Functions

1. `admin-set-user-active` (recomendada): recibe `{ userId, active }`, comprueba con la sesión que quien llama es admin y usa `auth.admin.updateUserById` con `ban_duration`. Es lo único que necesita secreto.
2. `send-welcome-email` (opcional): solo si se quiere conservar el correo de bienvenida que hoy manda `mailService.js`.

Todo lo demás se resuelve con Auth, tablas con RLS y Storage.

## 4. Políticas RLS

| Tabla | Operación | Quién | Condición |
|-------|-----------|-------|-----------|
| `products` | SELECT | Cualquiera | `is_active` |
| `products` | SELECT | Admin | todas las filas |
| `products` | INSERT, UPDATE, DELETE | Admin | `is_admin()` |
| `profiles` | SELECT | Cada persona | `id = auth.uid()` |
| `profiles` | SELECT | Admin | todas |
| `profiles` | UPDATE | Cada persona | su fila; un trigger impide cambiar `role`, `is_active` y `email` |
| `profiles` | UPDATE | Admin | todas; un trigger impide que se desactive a sí mismo |
| `profiles` | INSERT, DELETE | Nadie | el perfil nace por trigger y muere con la cuenta de Auth |
| `carts`, `cart_items` | Todo | Dueña o dueño | el carrito es suyo |
| `orders`, `order_items` | SELECT | Dueña o dueño y admin | su pedido |
| `orders`, `order_items` | INSERT, UPDATE, DELETE | Admin | `is_admin()` |
| `storage.objects` (bucket `product-images`) | INSERT, UPDATE, DELETE | Admin | `is_admin()` |
| `storage.objects` (bucket `product-images`) | SELECT | Cualquiera | el bucket es público, se lee por URL |

`is_admin()` lee `profiles.role` de la base de datos, no del token del navegador, así que no se puede falsificar editando el JWT. El rol nace siempre como `customer`; los metadatos de registro no pueden pedir `admin` (probado).

## 5. Datos que hay que mover

| Dato | De | A | Cómo |
|------|----|----|------|
| Productos | tabla `productos` | `products` | `supabase/seed.sql` trae los 7 de ejemplo. Si en tu base local hay productos reales que subió el admin, exporta con `COPY`/CSV y cámbialos a los nombres nuevos |
| Usuarios | tabla `usuarios` | `auth.users` | **No se pueden copiar las claves.** Los hashes bcrypt de la base vieja no sirven en Supabase (a menos que se importen con la API de administración, que acepta hashes bcrypt `password_hash`). Lo simple: pedir a cada cliente que use "Olvidé mi contraseña" |
| Imagen subida | `backend/uploads/img_1778207684287_590444.webp` | bucket `product-images` | Subirla desde el panel y actualizar `image_url` |
| Imágenes de `i.ibb.co` | URL externas | `public/products/` o Storage | Cuando estén los PNG recortados |

## 6. Variables de entorno

| Variable | Dónde va | Público |
|----------|----------|---------|
| `VITE_SUPABASE_URL` | Frontend | Sí |
| `VITE_SUPABASE_ANON_KEY` (clave publicable / anon) | Frontend | Sí; la protege RLS |
| `SUPABASE_SERVICE_ROLE_KEY` | Solo Edge Functions, como secreto de Supabase | **Nunca** en el frontend ni en Git |
| `GOOGLE_CLIENT_ID` y `GOOGLE_CLIENT_SECRET` | Panel de Supabase > Authentication > Providers | El secreto no |
| SMTP (host, usuario, clave) | Panel de Supabase > Authentication > SMTP | La clave no |

Las variables de `backend/.env` (`DB_*`, `JWT_SECRET`, `SMTP_*`) dejan de usarse al final de la migración.

## 7. Qué falta para conectar

1. Crear el proyecto en supabase.com (lo hace el dueño; hace falta su cuenta).
2. Aplicar `0001_schema.sql` y luego `seed.sql`.
3. Crear la cuenta de administrador y promoverla (instrucciones al final de `seed.sql`).
4. Configurar Auth: largo mínimo de clave 8, correo de recuperación con `{{ .Token }}`, Google, SMTP propio.
5. Copiar la URL y la clave pública en `.env` (a partir de `.env.example`).
6. Escribir el repositorio de productos y el servicio de Auth en `src/lib/supabase/` con las equivalencias de arriba.
7. Escribir las pruebas de paridad (registro, login, logout, recuperar, Google, perfil, productos, carrito, WhatsApp, admin, imágenes).
8. Solo con todo en verde, retirar Express y sus dependencias.

## 8. Riesgos

| Riesgo | Mitigación |
|--------|-----------|
| Perder las cuentas actuales | Son pocas y de desarrollo; pedir restablecer clave o importar con la API de administración |
| Políticas mal escritas dejan datos abiertos | Se probaron con 3 roles; repetir la prueba contra el proyecto real con el Security Advisor de Supabase |
| El navegador manda un `role: admin` en los metadatos | El trigger lo ignora |
| Clave `service_role` filtrada | Solo en secretos de Edge Functions; revisar `git grep service_role` antes de cada commit |
| Dejar `is_active` sin efecto real | Edge Function `admin-set-user-active` |
